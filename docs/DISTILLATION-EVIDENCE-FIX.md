# 分批提炼引用失败与耗时诊断

## 已知事实

用户截图报错为“AI引用与实际资料不匹配”。这是引用校验失败，不等于网络超时。无法仅凭截图确定失败的具体原文，未读取或更改用户本机数据库。

导图/闪卡默认采用完整文字提炼，不是旧版抽取前几个片段：B批正文提炼 + 1次跨课件合并 + 1次成果组织。没有缓存时通常需B+2次模型调用。去掉页码面板后，新任务默认处理整份所选资料，资料更多时批次和耗时也可能增加。每次模型请求可等待最多约90秒，因此整个任务不能承诺固定几秒完成。删除确认按钮只简化操作，不会减少后台步骤。

原协议让模型逐条抄写8至400字引文，再验证其是否出现在对应正文中。仅空白差异已被容忍，但文字改写、标点改动、引用错页等仍会导致整批拒绝。这是质量控制的脆弱接口；不能据此断言用户此次失败具体属于哪一种。

## 本次修复

1. 后端从原文生成带唯一编号的原文窗口（每段最多300字符，相邻窗口重叠80字符），向模型提供全部窗口，不再重复提供整块正文。
2. 模型提炼知识时选择当前资料块的原文编号，后端从原始窗口填入quote，再通过原有引用校验；不让模型重抄长引文。
3. 不存在的编号、其他资料块的编号均拒绝；若模型额外提供quote，仍验证该引文，不能借有效编号混入伪造引文。
4. 兼容旧版逐字引文及已经通过校验的私人批次缓存，不重建数据库、不强制重跑成功批次。
5. 提炼请求显式传递当前学习等级；保留资料权限、版本核对、分类、概念覆盖与冲突校验。
6. 新错误包含批次位置和资料ref，已完成批次保留。失败批次不会因点击一次而自动付费重试。
7. 后端日志记录任务ID、页数、批次、缓存数、各模型阶段的调用数和耗时，不记录密钥、问题或正文。前端生成提示显示页数及批次。

此改动降低模型抄写引文的负担，不保证模型一定成功选对编号，也不证明知识句必然被引文语义支持；后者仍需质量抽查。重叠窗口会增加部分输入字符，实际延迟、token成本及真实模型成功率需要用同一组真实PPT测量，未宣称已量化提速。

## 验证

使用隔离数据库和模型替身，不调用用户付费接口：

- 正常多PPT导图、闪卡缓存复用，保存的引文确实在对应原文中。
- 无效编号、跨块编号、额外伪造引文、遗漏正文块、遗漏概念、重复闪卡、资料冲突均不能冒充成功。
- 旧逐字引文仍可生成；编号不会跨资料块混用。
- 中途失败可复用已完成批次；权限和指纹仍有效。
- 全部后端测试和浏览器流程回归。

## 本机更新与复测

1. 在 `feat/development-foundation` 分支执行 `git pull --ff-only`。
2. 在后端终端按Ctrl+C停止，重新执行原后端启动命令；仅刷新前端不会加载新后端逻辑。
3. 刷新网页，先保持相同资料选择，点击失败任务的手动重试按钮或重新生成。旧失败任务本身仍保留失败记录。
4. 如仍失败，分享新的错误提示和带“[知识提炼]”的阶段日志，不提供Cookie或API密钥。根据批次与耗时判断卡在提炼、合并还是组织阶段，避免反复盲点生成。
