# 第一次技术实践：问答请求追踪与关键词检索排查

记录日期：2026-10-27。项目：操作系统课程 AI 助教系统。本文根据本次实际浏览器观察、Python实验、仓库代码和终端日志整理，可作为个人学习记录；不代表已经独立掌握全部实现。

## 1. 我们刚才做的流程叫什么

可以称为：**一次问答请求的端到端追踪与检索问题排查**。

具体做了网络请求观察、代码调用链阅读、最小复现实验、日志定位、代码修复和回归验证。这是后端开发和AI应用开发中的日常工程实践；本轮没有部署分布式链路追踪系统，也没有安装OpenTelemetry等框架。

本次技术问题属于**RAG中的检索质量问题**。RAG是“先检索资料，再把依据交给生成模型”的方法，不要求必须使用向量数据库。当前项目已经有关键词检索辅助生成的流程，仍有很多质量边界，不能称作完整成熟的教学RAG系统。

## 3. 从浏览器找到了什么

打开开发者工具 → 网络 → Fetch/XHR → 清空旧列表 → 重新提问 → 点击ask请求。

### 标头：请求发到哪里

```text
请求URL：http://127.0.0.1:5173/api/student/personal/ask
方法：POST
HTTP状态：200 OK
返回格式：application/json
```

5173是浏览器访问的前端开发服务地址，/api由项目代理转往后端；不能根据浏览器URL就认为AI模型运行在5173。200表示接口成功返回，不证明检索相关、引用充分或回答正确。

### 负载：网页发了什么

最初观察到的问题、章节记录编号、父任务编号、所选资料和开关，类似：

```json
{
  "question": "请用一句话解释什么是磁道",
  "chapter_id": 1,
  "parent_id": 33,
  "sources": [{"document_id": 20, "start_page": 1, "end_page": null}],
  "use_sources": true,
  "request_key": "此处省略实际请求标识"
}
```

chapter_id=1是数据库记录ID，不等于教材第一章。parent_id关联本人之前的学习任务，供后端恢复上下文；request_key用于识别重复请求。end_page=null表示请求没有明确结束页，代码再采用资料总页数。

### 预览：后端返回了什么

| 字段 | 含义 |
|---|---|
| body.answer | 回答正文 |
| body.basis | 系统标记的回答依据类别，不能当作正确性证明 |
| body.citations | 回答列出的引用，需检查引用是否真的支持结论 |
| sources.chunks | 系统选取的资料片段，不等于所有片段都被回答引用 |
| chunks中的ref/document_id/page/text | 片段标识、资料ID、物理页码、正文 |
| sources.method | 当前检索方法说明 |
| sources.warnings | 文字解析、图片/图表/动画等能力限制 |
| status=ready、error为空 | 任务已就绪且未记录错误，不等于答案已经人工核对 |

数组里的0、1、2是元素位置，不是PPT页码。page才是标注的资料页码。本记录不收录Cookie、登录令牌和API密钥；排查截图应遮挡这些内容。

## 4. 对应到哪些代码

```text
网页输入问题
  → frontend/src/personal.ts：personalApi.ask
  → /api/student/personal/ask
  → backend/app/personal_chat.py：ask
  → backend/app/personal_sources.py：retrieve
  → 问题与片段交给模型适配器
  → 校验、保存个人任务并返回
  → 网页显示回答
```

这是调用链的概括；前端request封装、后端认证、数据库持久化和模型适配器仍需逐步深入阅读。

- personal.ts把question、sources、use_sources等参数通过JSON.stringify编码为请求正文，再以POST发送。
- personal_chat.py通过body读取请求，检查学生身份、章节和资料访问权限，准备历史上下文。
- /ask路径与APIRouter前缀分开定义，因此搜索完整URL不一定能找到Python入口。
- scripts/personal-browser.cjs属于自动化测试，存在模拟请求处理，不是正常业务处理入口。

## 5. 亲手验证的Python基础

### 空白问题检查

```python
question = "   "
question = question.strip()
print(repr(question))  # ''
print(not question)    # True
```

strip清理两端空白，空字符串在条件判断中为假，not把它反转为真。空问题进入422处理，不继续处理模型请求。repr让不可见的空字符串更容易观察。

### 资料选择开关

```python
selected_sources = [{"document_id": 20}]
use_sources = False
sources = selected_sources if use_sources else []
```

开关关闭时得到空列表，不会删除上传资料。改变开关后必须重新执行赋值，变量不会自动重新计算。

### 位置编号与分数不同

```python
scores = [8, 0, 4]
# 编号      0  1  2
print(scores[1])  # 0
```

scores[2]取出第三个位置的分数4。best=[0,2]表示选片段0和2，不是分数0和2。

## 6. 当前检索怎么工作

1. 检查用户对所选资料的访问权限。
2. index_document取得可提取文字的索引；已有匹配签名的索引可以复用。
3. 收集所选页码范围内的片段，按ref去重，组成pool。
4. terms提取词项：英文/标识符使用词项，连续中文使用相邻双字片段（character bigram）。这不等同于中文语义分词。
5. 计算各候选片段的加权匹配分数。
6. 快速普通提问按分数排序，最多取8项，然后排除0分项；资料概览采用另一个轮流选取分支。
7. 按24000字符预算构造最终片段，资料不足时给出错误/警告。
8. 将依据交给问答生成流程；回答后再次检索核对资料指纹是否变化。

24000是Python字符串长度预算，不是模型token数量。当前快速检索可能只索引长页前4000字；不因此声称完整理解了PPT图片、图表、动画或代码图片。

### 打分涉及哪些技术

当前是**词频与逆文档频率思路的词项加权打分**，类似TF-IDF思路，不是标准BM25，也不是向量相似度或模型语义评分。这里的“文档频率”按候选片段统计，不是文件数量。

```python
(1 + math.log(c[t])) * math.log(1 + len(pool) / (1 + frequency[t]))
```

- t：当前检索词。
- c[t]：该词在当前片段的出现次数，只有命中才参与计算。
- len(pool)：候选片段总数。
- frequency[t]：包含该词的候选片段数。
- 所有命中词的贡献相加，得到片段总分；log减缓重复词带来的增长。

“出现同一个词”不等于“包含所需答案”，这一点不能由数学公式自动保证。

## 7. 发现并修复的第一个问题

原代码取排序后前8项，只在所有分数都是0时拒绝。只要有正分，0分片段也可能混入前8项。

独立实验：

```python
scores = [2, 5, 0, 5]
best = sorted(range(len(scores)), key=lambda i: (-scores[i], i))[:4]
print(best)  # [1,3,0,2]
best = [i for i in best if scores[i] > 0]
print(best)  # [1,3,0]
```

排序时高分在前，同分保持原位置先后。新增过滤只用于普通提问且存在正分的分支；概览和全0分分支保留。

独立实验还验证了混合分数、全0分和同分情况，但不能代替项目真实检索测试。

## 8. 怎样确认项目真的生效

开始手动加入print后没有看到输出，不能直接断定是语法错误。入口可能未调用、走了不同分支、修改未保存，或运行文件不同。本轮并没有取得足够证据确认当时不打印的唯一原因。

后来在GitHub提交了过滤和正式INFO日志，提交为68affc4，使用Uvicorn默认日志通道。日志区分：

- 未启用结合资料；
- 未选择资料；
- 已进入retrieve及实际代码路径；
- 概览或完整提炼分支；
- 普通检索过滤前后分数；
- 检索无可用依据、转为通用解释。

日志不打印用户问题、资料正文、Cookie或密钥。看到端口8000占用时先停止旧后端，不盲目结束进程。

### 本机实际观察到的结果

```text
资料数=2
模式=quick，概览=False
过滤前：[7.1946, 3.2055, 3.2055, 0, 0, 0, 0, 0]
过滤后：[7.1946, 3.2055, 3.2055]
返回片段数=3，候选片段数=71
```

结论：本次前8项的5个0分项被排除。不能由此声称回答准确率提高了某个百分比。

相同日志出现两次对应生成前检索与生成后的资料一致性检查，不等于模型调用两次。

仓库验证：相关29项和当时全量211项后端测试通过，模型使用模拟响应；这不等于真实模型质量已全部验收。详见[检索过滤与日志](../RETRIEVAL-FILTER-LOGS.md)。
