# 操作系统课程 AI 助教系统：代码复查与下一周优化报告

编写日期：2026-10-15（中国标准时间）。代码基线：`fac6534`，分支 `feat/development-foundation`。

本报告是优化规划，不表示建议功能已实现。本轮只做代码、数据库与公开参考资料检查，并重新运行既有测试；不将外部项目成果记为本项目成果。

## 1. 工程判断与一周目标

现有 V0.2 已经解决“账号能登录、角色能区分、内容能发布、私人资料不串号、基础算法能计算”的问题。下一周最有价值的工作是把它变成一条可信、可讲解的教学路径：

> 教师上传有来源的资料 → 解析并审核正文 → 关联章节/知识点并发布 → 学生阅读资料 → 单步观察 FCFS → 完成关联练习。

建议交付 V0.2.1，重点是**真实课程内容、资料可追溯、FCFS 可教学、界面可用**。SQLite、React、FastAPI 继续使用。整套组件库替换、PostgreSQL 迁移、向量数据库、完整 RAG、多个复杂动画不作为这一周的必交项。

完成标准是演示上述闭环，而不是增加很多菜单。最低闭环无需真实模型密钥；资料检索可以先返回原文片段，AI 必须在具备检索与引用校验后才称为资料辅助问答。

## 4. 数据库优化方案

### 4.1 继续用SQLite

目前内容量与本地并发不需要更换数据库。先补迁移纪律、元数据、查询与备份恢复，比换ORM或数据库更有收益。维持参数化SQL；提取少量共享查询，避免main/files/learning/teaching互相分散授权逻辑。

计划迁移：

| 版本 | 目标 | 安全要求 |
|---|---|---|
| 003 | 资料来源/摘要/哈希/解析元数据，章节/知识点必要更新时间，检索所需索引 | 旧资料字段允许空，保留ID/文件名/owner；已发布资料不自动撤销 |
| 004 | 文档页或文本单元、分段表；可选解析任务记录 | 不把原documents.content当唯一全文；解析失败保留原文件与元数据 |
| 005（可选） | knowledge学习记录、可选实验运行记录 | 用户隔离；只记录真实行为，测试脚本不污染用户库 |

迁移文件可放 `backend/app/db_migrations/`，仅抽取这一职责，不顺便重写所有服务。每个迁移在事务内标记版本；涉及SQLite重建旧表的步骤另行设计，执行前备份并验证计数/关系/文件清单。迁移前停服务，避免数据库快照与文件复制期间有并发写入。

### 4.2 建议字段与表

`documents` 增量字段按实际必需拆批加入：

| 字段 | 用途 |
|---|---|
| summary | 列表/卡片摘要，与原文分离 |
| source_title/source_url | 书名、网站或仓库来源，不把文件名当出处 |
| author/license/license_url | 可复用范围与来源登记；未知则标记待审核 |
| sha256 | 文件完整性与重复上传提示 |
| parse_status | pending/parsing/ready/failed/unsupported，明确模型可否检索 |
| parse_error | 不含秘密信息的失败原因 |
| parser_version/content_version | 重新解析与索引失效判断 |
| page_count/published_at | 资料规模和真实发布时间；旧资料没有可靠时间时保持空，不能伪造 |

不要把所有字段一次强制设为NOT NULL，否则旧数据会升级失败。

正文层：

- `document_pages(id,document_id,page_index,page_label,text)`：PDF文件页索引与印刷页码分开；TXT可使用文本单元并保存行范围。没有识别出的印刷页码不编造。
- `document_chunks(id,document_id,page_id,chunk_index,text,start_offset,end_offset,content_version)`：offset按Unicode字符而非字节约定；段落跨页时先避免合并，保证引用可定位。
- `learning_records(user_id,knowledge_point_id,last_viewed_at)`：可选最小持久化继续学习。实际打开只记为访问，不自动推断“已掌握”。

本周不必新增大而空的知识图谱、向量表、学习画像和复杂成绩模型。

### 4.3 去重与权限

文件哈希不能直接对全库做“重复文件已存在”提示，否则会向学生泄露其他人的上传事实。第一版只在“同一owner的个人资料”或“教师可管理的公共资料范围”内提示重复；不做跨用户物理文件去重，避免共享文件删除问题。

索引建议先验证查询计划，再选加：章节(course_id,published,sort_order)、知识点(chapter_id,published)、资料(course_id,category,published,chapter_id)、本人资料(owner_id,category)、用户问答(user_id,id)。关系表已有(document_id,knowledge_point_id)主键，可视反向查询增加(knowledge_point_id,document_id)。

## 5. 公共资料“投喂”的正确工程路线

### 5.1 三个阶段

1. **课程内容入库**：文件、来源、章节、知识点、发布状态完整，学生能阅读。
2. **原文解析与检索**：把PDF/TXT转为可定位的正文单元，能按章节/关键词找到片段。
3. **检索辅助问答**：只把当前用户可读片段发给模型，附来源，缺证据时明确说明。

这条路线不修改模型权重，不是训练或微调。现有代码只完成了第1阶段的一部分；后端接受一个material_id并直接拼正文，也不等于完成检索。

### 5.2 下一周的最小资料集

先选“进程与线程”“处理机调度”两个章节，完成一条高质量示范路径，而非一次填满全书：

- 8–12个知识点：进程/线程、三态转换、调度指标、FCFS、短作业优先思想、抢占与非抢占、上下文切换等。
- 6–8份有来源资料，其中至少2份文本型PDF、2份UTF-8 TXT，其余可为自主整理讲义；可包括故意不支持的扫描件测试样本，但不应发布为可检索资料。
- 10–15道人工校对选择题，覆盖概念与至少3道FCFS计算题。
- 3组算法示例继续保留，增加1组小数时间或极端长空闲输入用于验证。

数量是建议验收范围，不是当前已有内容。其余5章保持清晰导航，逐周补齐。你先确认真实教材版本、章节名称和允许使用的课程资料；工程侧负责登记、校验和导入。

### 5.3 导入流水线

```text
选择来源 → 登记许可/出处 → 类型大小检查 → 范围内哈希去重
→ 保存原文件与元数据 → 解析正文 → 预览/纠错
→ 按页和段落分段 → 关联章节/知识点 → 教师审核发布
→ 授权检索 → 学生阅读/可选AI引用
```

首版使用人工触发的本地解析命令或有明确状态的处理函数，不引入Redis/Celery。PDF解析需设置页数、运行时间和可接受输出量上限；具体阈值用样本确认。失败后可重试，不吞异常；新解析结果验证通过后再替换旧索引。扫描PDF显示“未检测到文本，暂不支持OCR”，不能假装提取成功。

可优先评估pypdf做文本型PDF提取，锁定版本；先实测中文、多栏、表格、公式，再决定是否需要更强解析工具。复杂公式不保证无损，必要时保留原文件页阅读。

### 5.4 本周检索与AI范围

必交：章节约束、标题/关键词检索，返回文档名、页码/行范围、原文片段、可访问文件链接；无结果明确提示。

小规模先做可解释关键词基线，不急于上向量数据库。中文不能默认认为SQLite FTS5 unicode61就有良好分词；若使用FTS，要验证运行时支持、中文切词/子串策略及召回效果。

可选：若解析、权限和检索先通过，且用户提供可用模型配置，再做引用式回答。每条引用必须对应检索到且可读的chunk_id；生成后校验引用ID，不虚构页码。文档中的指令视为引用数据，不允许其改变系统规则。不在本周承诺细粒度“每句话完全被证据支持”的自动证明。

取消发布或删除资料后，新检索与新问答必须立即不可使用它；旧聊天可能包含历史摘录，另行决定是否保留、隐藏或标记“来源已撤回”，不能假设撤回文件就自动收回旧回答或本地下载副本。

- 教师资料：上传表单和编辑表单各自保存状态；资料列表有章节、发布、解析状态过滤；保存后提示实际结果。关联知识点随章节筛选，并能看到已选跨章节知识点。

## 7. 算法与动画方案

### 7.1 先FCFS教学播放器，后扩展算法

当前fcfs是57行纯Python，结构适合独立测试，应保留。第一版动画目标：学生在任意时刻能回答“谁在等待、谁在执行、为什么轮到它、指标怎么得出”。

建议将结果协议补充为：

```json
{
  "algorithm": "fcfs",
  "schema_version": 1,
  "results": [],
  "timeline": [],
  "events": [
    {"time": 0, "type": "arrival", "pid": "P1"},
    {"time": 0, "type": "dispatch", "pid": "P1"},
    {"time": 4, "type": "complete", "pid": "P1"}
  ]
}
```

这是建议协议，不是现有API返回。events、timeline和最终指标必须从同一份调度计算生成，不能由前端或模型再计算另一套结果。纯函数build_state(processes,events,cursor)还原播放状态，以便前进、后退、跳转和回放。

### 7.2 语义与边界先定清

- 同时到达按输入顺序；P1完成与P2在同一时间到达时，先记录完成、再纳入同一时刻到达、再派遣；全程定义稳定顺序。
- 对时间点t，累计等待为已到达且未运行区间长度；未完成进程的周转值需标为进行中，不提前显示最终结果。
- timeline沿用半开区间[start,end)，结束点状态切换规则一致。
- CPU空闲直接是一个时间段，不生成百万个逐时间单位帧。
- 小数时间和长空闲只用事件/时间坐标处理，不能依赖整数for循环。
- 使用内部进程标识映射颜色；用户pid仅展示，避免用显示文字“CPU空闲”判断状态。

### 7.3 播放器界面

必需：播放、暂停、上一步、下一步、重置；当前模拟时间、CPU、就绪队列、已完成列表、当前步骤解释；甘特图当前游标。倍速与进度拖动在基础控制稳定后加。

用SVG绘制甘特图与游标，CSS负责高亮和轻微过渡；暂不需要D3、Canvas或3D。模拟时间与真实播放速度分离，暂停不能继续推进；多次点击播放只允许一个计时器，卸载/重置必须清理。减少动态效果的系统设置应得到尊重。

SJF非抢占可作为附加目标，但必须先通过FCFS播放器验收。RR、SRTF、MLFQ放下一轮，因为抢占、时间片与同刻事件会显著增加测试负担。页面置换FIFO/LRU适合之后做第二类实验，不建议这一周同时开工。

### 7.4 测试与可对比规则

保留现有三组例子；增加事件序列、同刻完成/到达、小数时间、长空闲、重置重播、单步最终状态与API指标一致性测试。对每个进程检查等待≥0、完成=开始+运行、周转=完成−到达、非空闲区间长度之和=总运行时间。

与外部模拟器对比前必须统一假设。OSTEP cpu-sched示例的运行时输入不能直接当作支持任意arrival的基准；可先比较所有arrival=0的公共子集，其余输入用人工推导和本项目不变量验证。
